# 裸机 vs 容器推理初始化耗时对比分析报告

## 一、数据概览

本报告对比分析了裸机并发运行推理和容器并发运行推理在不同并发数（n=1 到 n=16）下的初始化耗时表现。

## 二、各项初始化指标随并发数的变化

### 2.1 init_ms（初始化总时间）

**裸机表现：**
- n=1: 2729.79ms
- n=16: 17815.89ms
- **增长趋势：线性增长，约为 6.5 倍**
- **特点：随并发数增加显著增长**

**容器表现：**
- n=1: 486.15ms
- n=16: 2616.46ms
- **增长趋势：增长约 5.4 倍**
- **特点：基线低，增长相对平缓**

**对比结论：**
- **裸机 init_ms 始终远高于容器**
- n=1 时，裸机比容器高 **2243.64ms**（约 4.6 倍）
- n=16 时，裸机比容器高 **15199.43ms**（约 6.8 倍）
- **差距随并发数增加而扩大**

### 2.2 import_ms（导入时间）

**裸机表现：**
- n=1: 2345.00ms
- n=16: 15706.31ms
- **增长趋势：增长约 6.7 倍**

**容器表现：**
- n=1: 4064.00ms
- n=16: 42281.00ms
- **增长趋势：增长约 10.4 倍**

**对比结论：**
- **容器 import_ms 始终高于裸机**
- n=1 时，容器比裸机高 **1719.00ms**（约 1.7 倍）
- n=16 时，容器比裸机高 **26574.69ms**（约 2.7 倍）
- **容器的 import_ms 随并发数增长更快**

### 2.3 load_ms（模型加载时间）

**裸机表现：**
- n=1: 132.00ms
- n=16: 1157.81ms
- **增长趋势：增长约 8.8 倍**

**容器表现：**
- n=1: 235.00ms
- n=16: 1293.31ms
- **增长趋势：增长约 5.5 倍**

**对比结论：**
- 容器的 load_ms 略高于裸机
- 两者都随并发数增加而增长
- 在低并发时差距较小（约 100ms），高并发时差距也相对有限

### 2.4 warmup_ms（预热时间）

**裸机表现：**
- n=1: 58.00ms
- n=16: 814.56ms
- **增长趋势：增长约 14 倍**

**容器表现：**
- n=1: 66.00ms
- n=16: 341.38ms
- **增长趋势：增长约 5.2 倍**

**对比结论：**
- 低并发时（n≤8）容器略高
- **高并发时（n≥10）裸机反而更高**
- n=16 时，裸机比容器高 **473.19ms**

## 三、关键发现与解释

### 3.1 init_ms 的含义差异

通过对比 `init_ms` 与 `(import_ms + load_ms + warmup_ms)` 的总和，我们发现：

**裸机的 init_ms：**
```
n=1:  init_ms = 2729.79ms,  import+load+warmup = 2535.00ms
差值: +194.79ms
```
- **init_ms 略大于三者之和**
- 差值（194.79ms）代表：**进程启动开销**，包括：
  - Python 解释器启动时间
  - 基础环境初始化
  - 进程间通信建立
  - 其他系统调用开销

**容器的 init_ms：**
```
n=1:  init_ms = 486.15ms,  import+load+warmup = 4365.00ms
差值: -3878.85ms （init_ms 远小于三者之和）
```
- **init_ms 远小于三者之和**
- 这表明 **init_ms 在容器场景下的定义不同**：
  - **init_ms 主要是容器启动时间**，包括：
    - 容器创建和启动
    - 网络命名空间建立
    - cgroup 资源限制设置
    - 文件系统挂载
  - **不包括容器内的 Python 导入、模型加载等时间**

### 3.2 为什么裸机的 init_ms 反而更大？

这是因为 **init_ms 在两种场景下测量的时间段不同**：

#### 裸机场景：
```
init_ms = 进程启动 + import + load + warmup + 其他开销
≈ 2730ms (n=1)
```
- 包含了 Python 解释器启动后的所有初始化步骤
- 测量的是 **从启动到完全就绪** 的总时间

#### 容器场景：
```
init_ms = 容器启动时间（不包括容器内的初始化）
≈ 486ms (n=1)

容器内初始化 = import + load + warmup
≈ 4365ms (n=1)
```
- init_ms 只测量 **容器基础设施的启动时间**
- import/load/warmup 是在容器启动后单独测量的
- **容器启动本身很快，但容器内的导入很慢**

### 3.3 为什么容器的 import_ms 比裸机高这么多？

容器的 import_ms 显著高于裸机，原因包括：

1. **文件系统层叠开销**
   - 容器使用 overlay2/aufs 等联合文件系统
   - 多层镜像导致文件访问路径更长
   - I/O 性能有一定损失

2. **冷启动效应**
   - 容器刚启动，文件系统缓存为空
   - 裸机可能有部分系统级缓存

3. **Python 包的碎片化**
   - Python 导入时需要读取大量 .py/.pyc 文件
   - 容器文件系统的多层结构放大了这个开销

4. **并发竞争**
   - 高并发时，多个容器同时进行大量 I/O
   - 容器的资源隔离可能导致更多的上下文切换

## 四、并发扩展性分析

### 4.1 总初始化时间对比（import + load + warmup）

| 并发数 | 裸机总和(ms) | 容器总和(ms) | 容器/裸机比值 |
|--------|-------------|-------------|--------------|
| 1      | 2535        | 4365        | 1.72x        |
| 2      | 1709        | 4360        | 2.55x        |
| 4      | 3502        | 8796        | 2.51x        |
| 8      | 7145        | 17995       | 2.52x        |
| 16     | 17679       | 43916       | 2.48x        |

**结论：**
- 容器的实际初始化时间（import+load+warmup）约为裸机的 **2.5 倍**
- 这个比例在不同并发数下相对稳定

### 4.2 并发扩展性

**裸机：**
- import_ms 从 2345ms 增长到 15706ms（6.7x）
- 相对线性增长，扩展性较好

**容器：**
- import_ms 从 4064ms 增长到 42281ms（10.4x）
- 增长更快，说明并发扩展性相对较差
- **原因：容器间的资源隔离和竞争在高并发时更明显**

## 五、结论与建议

### 关键结论：

1. **init_ms 的含义不同**：
   - 裸机：包含完整的初始化流程
   - 容器：仅指容器启动时间，不包括容器内初始化

2. **真实初始化成本（import+load+warmup）**：
   - 容器约为裸机的 2.5 倍
   - 主要差距在 import_ms（文件系统开销）

3. **并发扩展性**：
   - 裸机扩展性更好
   - 容器在高并发时初始化开销增长更快

### 优化建议：

**对于容器场景：**
1. 使用容器镜像缓存和预热
2. 优化镜像层数，减少文件系统层叠
3. 考虑使用 volume 挂载方式加载模型
4. 预先导入常用 Python 包，制作专用基础镜像

**对于裸机场景：**
1. 进程池复用，避免频繁启动
2. 考虑使用 fork 模式复制已初始化的进程

**对于高并发场景：**
1. 如果追求启动速度，裸机方案更优
2. 如果需要资源隔离，容器方案需要额外优化
3. 考虑混合方案：预启动容器池，减少冷启动
